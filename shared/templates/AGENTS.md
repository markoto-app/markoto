# Templates

A template is a **bundle: a starting text + the design it is written for** (a built-in theme preset). The new-document dialog offers the bundles as ONE choice (no separate content / design rows); the design can be changed later in the theme panel. Registry entries (`TEMPLATES` in `index.ts`): `id` (stored in `documents.templateId`, never renamed), `content` (body directory under `content/`), `design` (preset id; `null` only for `blank` = the user's default design: the workspace default, else markoto), `category` (the picker tab, same set as `ThemePreset.category`; `general` only under All), icon, i18n keys `templates.<id>.{label,description}` (all six UI locales), optional `cover` placeholders per locale (subtitle / authors / affiliations / `showDate`) for designs whose cover or title block shows them. Every built-in preset has at least one template (pinned by `tests/unit/templates.test.ts`).

Shipped: demo (the dialog's default for a first document, `DEFAULT_TEMPLATE_ID`; markdown cheat sheet + where sharing, themes, cover page, comments + `@markoto`, the AI bar, dictation, activity/restore, PDF export and workspace knowledge live; all six UI locales), blank (truly empty — no body at all), resume (NOT a skeleton: a filled-in one-page CV for a made-up person, sized to one A4 page with the `resume` preset; all six locales; `/templates/resume` previews it verbatim, pinned by `tests/unit/templates.test.ts`), and skeletons for engineering (runbook, design-doc, api-reference, project-readme → `tech-docs`), academic (arxiv, ieee-conference, thesis, lecture-notes, essay = APA), business (report and business-plan → `business-report`, proposal, one-pager, memo, meeting-notes → `modern`) and writing (manuscript, newsletter, recipe → `modern`). Skeletons have the heading hierarchy the genre needs, section-level `<!-- ... -->` instruction comments — invisible in preview/PDF (comment plugin in `app/utils/AGENTS.md`) but visible in the markdown source AND in the AI's `view_document` calls — and short visible scaffolding where the genre has a fixed format (tables with header rows, `Table:` captions, run-in labels, endpoint fences, alerts, task lists), so the first page already looks like the genre in its design. A design with a cover page or title block prints the title, so those texts don't start with `# {{title}}` (pinned); `memo` puts `{{title}}` in its Subject line.

**Retired ids** live in `TEMPLATE_ALIASES` (`academic-paper` → `arxiv`): `isTemplateId` accepts them, `resolveTemplateId` / `getTemplate` map them, `POST /api/docs` / `PUT /meta` / Markdown import store the current id, `renderTemplate` renders the new template for old documents. `TEMPLATE_IDS` (and the AI/MCP `template_id` enum) list current ids only.

**Pictures:** `public/template-thumbs/<id>.webp` — the first page of the English text in its design, with the cover placeholders and a sample title from `tests/fixtures/theme-shots/template-thumbs.json`; rendered by `make template-thumbs URL=… [IDS=…]` (`scripts/render-theme-thumbs.ts --templates`), hashes in `templateThumbnails.manifest.json`, URL via `thumbnails.ts#templateThumbnailUrl`. `tests/unit/templateThumbnails.test.ts` fails when a template's text, design or placeholders changed without a new picture.

**Server side** (`server/utils/createDocument.ts`): theme precedence `themeId` → `themePreset` → the template's design → workspace default → schema default. The template's `cover` placeholders are filled into empty cover fields only when the document gets the template's own design (implicitly or `themePreset === design`), in the document language. So `POST /api/docs {templateId}` alone gives the bundle; `templateId` + `themePreset` (marketing `::cta`, MCP/AI `theme_preset`) still overrides the design. The AI / MCP `create_document` tool describes each template with its design (`TEMPLATE_TOOL_HINT`).

Adding a template: `content/<id>/en.md` + `de.md` (both mandatory, pinned) + a `TEMPLATES` entry + i18n keys in all six locales + a sample title in `template-thumbs.json` + `make template-thumbs IDS=<id>`.

## Split between client-safe registry and server-only renderer

- **`index.ts` (this directory)** — registry only (id, content dir, design, category, icon, i18n keys, `hasContent`, cover placeholders, aliases, `TEMPLATE_LOCALES`, `templateLocale`, `isTemplateId` / `resolveTemplateId`). Imports cleanly into client + server bundles.
- **`server/utils/templateRenderer.ts`** — `renderTemplate(id, ctx)` (id or alias) reads the `.md` files from `content/<template.content>/<locale>.md` via `fs.readFileSync` (cached at module load), substitutes `{{title}}` / `{{description}}` placeholders, returns null for `blank` and unknown ids.

**Why the split:** Vite's `?raw` import works for the client bundle but Nitro's rollup pipeline doesn't, so a unified `shared/` import would 500 SSR. Server-only rendering means the body is shipped as a fully-substituted string on the token endpoint — the client never has to load template files. The `?raw` symptom looks like `Error: Could not load .../en.md?raw — ENOENT`; if you see it, the import lives in `shared/` and needs to move to `server/`.

## Multilingual

Each template ships per-locale files (`demo`, `report` and `resume` in all six UI locales, the skeletons `en.md` + `de.md`; `TEMPLATE_LOCALES` lists all six, a missing file falls back to English). Locale resolution in `renderTemplate`: exact match → BCP-47 base (`de-CH` → `de`) → English fallback. Free-text languages drop to English without throwing; the AI handles output language via the doc-context block regardless. Adding a locale = drop new `.md` files + extend `TEMPLATE_LOCALES` once (and add cover placeholders for it where a template has them).

## Seeding flow

Server token endpoint pre-renders the body (with the doc's title/description, locale-matched on doc.language) and ships it as `initialBody` on every fetch. Client uses it only when `ytext.length === 0`, so re-fetching the token on a doc with content is harmless. `blank` renders to null and the document stays empty (there is no generic welcome text any more). An empty `POST /api/docs` ("Just give me a blank doc", File → New) gets the schema default `blank`. The Demo text names real UI labels per locale (menu paths, button names): when one of those labels changes, update the demo files too.

## Gotchas

- **Templates use `fs.readFileSync` cached at module load, NOT lazy.** The body files are tiny (a few KB each) and frequently used. Reading once per process at first call beats both: re-reading per request (disk hit on every doc creation) and bundling them as JS strings (loses the human-readable `.md` authoring experience for translators).
- **Template body is shipped on the token endpoint, NOT the POST response.** POST response is just `{ docId }`. The client navigates to `/d/<id>`, the editor mounts, `useDocToken` calls the token endpoint, and `initialBody` rides back on that response. Putting the body on POST would lose it across the navigation. Re-fetching the token on a doc that already has content is harmless because the seed gate is `ytext.length === 0`.
- **`?raw` markdown imports work in Vite (client + Vitest) but NOT in Nitro/Rollup for `shared/`.** Fix: move the renderer to `server/utils/` and use `fs.readFileSync` with `import.meta.url`-relative paths. The body files stay in `shared/` for translator ergonomics + co-location with the registry.
